# Clean Code 摘要

- 書名：無瑕的程式碼：敏捷軟體開發技巧守則（第二版）
- 原文：*Clean Code: A Handbook of Agile Software Craftsmanship, 2/e*
- 作者：[[Robert C. Martin]]；譯者：盧國鳳；出版：博碩，2026-07
- 書籍資訊卡：[[Clean Code]]
- 類別：程式設計與技術
- 狀態：閱讀中（2026-10-16 開始）

第二版不是單純更新，而是整本改寫。全書分成四部分：程式碼、設計、架構、軟體工藝，範例涵蓋 Java、JavaScript、Go、Python、Clojure、C#、C。附錄收錄作者與 John Ousterhout 對程式品質的辯論。

**我的看法：為什麼讀**：希望自己寫的程式碼更容易閱讀，未來貢獻開源專案時，不會被認為是 AI 產生的低品質程式碼（[[Clean Code]]）。

## 全書主張（讀到目前為止）

為了省時間寫出的爛程式碼，最後會讓開發越來越慢；維持程式碼整潔才是長期走得快的方法（[[Clean Code 01 無瑕的程式碼]]）。整潔不是一次到位，而是先讓程式碼能動，再逐步清理（[[Clean Code 02 清理你的程式碼]]，見[[先讓它能動再讓它正確]]）。

## 章節摘要

### 01 無瑕的程式碼

**核心主張**：今天為了省開發時間寫出的爛程式碼，未來會像迴旋鏢一樣打回自己頭上，見 [[技術債]]（[[Clean Code 01 無瑕的程式碼]]）。

**重點**
- **邊寫邊整理**：整理是寫程式過程的一部分，不是事後才做的大掃除。
- **目標是好讀好改，不是完美**：讀的人好讀、改的人好改，即使多年後由別人閱讀也能輕鬆理解。
- **[[童子軍規則]]**：每次碰到程式碼，都讓它比原本乾淨一點。

**引文**
> 走得快的唯一方法，就是把事情做好。

> 先讓程式碼能運作，再讓它正確。

這句的原文概念是 *make it work, make it right*。right 指的是結構良好、整潔，不是「功能正確」。

> 簽入的程式碼要比簽出時更乾淨。

這句是[[童子軍規則]]的另一種說法。

**我的看法**：未來寫程式可能越來越講究責任到人，寫出品質好的程式碼就是在累積個人信用。

**我的行動**
- 改 bug 時，順手把難以閱讀的變數名稱改掉。

### 02 清理你的程式碼

**核心主張**：先寫出一份能執行的程式碼，再透過不斷調整讓它逐漸變好，見[[先讓它能動再讓它正確]]（[[Clean Code 02 清理你的程式碼]]）。

**重點**
- **先能動，再清理**：不要一開始就追求完美。
- **把類似的程式碼提取成函式**。
- **建立內部物件**：原本在輔助函式之間傳來傳去的引數，改成物件自己的欄位。
- **不要寫得太聰明、太複雜**：那樣反而不好。

**引文**
> 先讓它能運作，再讓它正確，或至少更好。

> 如果你覺得某件事很聰明、很複雜，小心，它很可能只是自我放縱。

**我的看法**
- 書中把檢查拆成兩個函式（檢查不合法的相鄰前綴組合、檢查字元重複次數過多）的做法，讓程式碼更清楚。
- 49NGO 那種字元替換的寫法太聰明，反而不自然，別人要花很久才讀得懂。
- 範例是 Java，我還不熟。

**我的行動**
- 下次看到自己寫的兩段幾乎一樣的程式碼，把它抽成函式。
- 建立內部物件，避免把引數傳來傳去給輔助函式。
